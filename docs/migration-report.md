# 存储格式迁移方案 — 汇报文档

**日期：** 2026-07-10  
**项目：** 南山知识库  
**事项：** 富文本编辑器存储格式从 Markdown 迁移至 ProseMirror JSON

---

## 一、为什么要迁移

当前富文本文档以 Markdown 格式存储。现在有三个需求，Markdown 无法满足：

1. **扩展编辑器排版能力** — 添加字体选择、文字颜色、高亮标记。Markdown 标准不支持这些语义，继续使用 Markdown 意味着这些样式保存后刷新即丢失。

2. **兼容性** — 拖拽缩放图片后产生 `<img>` HTML 标签，与文档中其他 `![alt]()` 标准 Markdown 语法混合存储。两种格式混存增加了维护复杂度。

3. **未来扩展** — 后续计划添加文档导出（PDF/DOCX/HTML）和 RAG 智能检索。结构化 JSON 格式更适合文本提取、分块和格式转换。

**核心判断：必须换存储格式，ProseMirror JSON 是正确选择。**

ProseMirror JSON 是编辑器（Tiptap）的原生数据格式，编辑器本身就是对这份 JSON 的可视化操作。用 JSON 存储意味着"编辑器里是什么样，存下来就是什么样"，没有转换损失。

---

## 二、可行性验证结论

正式开发之前，对 6 个核心假设进行了自动化验证，全部通过。

| 验证项 | 结论 | 数据 |
|--------|------|------|
| 离屏转换引擎与编辑器输出是否一致 | ✅ 一致 | 两个独立实例对 11 个样本输出完全相同的 JSON |
| 现有文档能否无损转换 | ✅ 可以 | 图片/表格/代码块/纯文本全部正确保留 |
| 字体/颜色/高亮能否正确保存恢复 | ✅ 可以 | 18 个场景全部通过，JSON 重载后样式不丢失 |
| 批量转换性能是否可接受 | ✅ 优秀 | 100 个文档纯转换仅需 1.3 秒 |
| 极端输入是否会导致崩溃 | ✅ 稳定 | 0 崩溃，超大文本(100KB)工作正常 |
| 移除旧序列化代码是否安全 | ✅ 安全 | JSON 路径完全不依赖被删除的代码 |

**唯一已知的边界情况：** `[](url)` 格式的无文本链接在 JSON 中无法表示（编辑器底层要求链接必须附着在文字上）。这种写法在实际文档中极为罕见，不影响迁移。

## 三、技术方案概要

### 3.1 存储格式

文档增加 `contentType` 字段来区分新旧格式：

| contentType 值 | 含义 |
|----------------|------|
| 不返回此字段 | Markdown（旧文档，向后兼容） |
| `"markdown"` | Markdown（旧文档） |
| `"prosemirror"` | ProseMirror JSON（新文档） |

### 3.2 图片处理

图片引用 `minio:文件ID` 的格式在两种存储方式中都保持一致。图片上传、预览 URL 获取的 API 完全不变。JSON 能额外保留图片的宽度/高度属性（缩放后信息不丢失）。

### 3.3 迁移策略：双层保障

| 层级 | 机制 | 触发时机 | 说明 |
|------|------|----------|------|
| **主路径** | 静默批量迁移 | 用户登录后自动触发 | 系统自动扫描所有旧文档并转换，用户无感知，不阻塞正常操作 |
| **兜底** | 按需迁移 | 用户编辑某个旧文档时 | 如果静默迁移遗漏了某个文档，编辑并保存时自动转换 |

### 3.4 静默迁移工作流程

1. 用户登录，进入主页
2. 系统后台检查是否有待迁移的旧文档
3. 如果没有 → 结束，用户完全无感知
4. 如果有 → 在浏览器空闲时间片中逐批转换（每批 10 个），不阻塞点击和输入
5. 全部完成 → 标记完成，用户无感知
6. 如果中途关闭页面 → 已完成的已保存，未完成的下次登录继续

### 3.5 性能数据

- 单个文档转换耗时：约 **13 毫秒**
- 100 个文档纯转换耗时：约 **1.3 秒**
- 加上网络写回的模拟耗时：约 **3 秒**
- 存储体积膨胀：纯文本文档约 1.5~3 倍，含表格文档约 6~12 倍

## 四、需要后端配合的工作

| 序号 | 工作项 | 优先级 | 说明 |
|------|--------|--------|------|
| 1 | 数据库增加 `content_type` 列 | 必须 | 新增列默认 NULL（NULL 表示 Markdown，兼容旧数据） |
| 2 | 接口返回 `contentType` 字段 | 必须 | `GET /text/get/{id}`、`PUT /text/update`、`POST /text/add` |
| 3 | 新增迁移列表接口 | 建议 | `GET /text/migrate-list` — 加速批量迁移 |
| 4 | 新增批量写回接口 | 建议 | `POST /text/migrate-batch` — 减少网络请求 |

如果第 3、4 项短期内无法实现，可以用现有接口逐文档处理，只是稍慢一些（多几十次 HTTP 请求），不影响功能。

## 五、影响范围

### 需要修改的文件：9 个

### 不受影响的部分

- Excel 编辑器
- 文件预览
- 图片上传和缓存
- 回收站
- 用户和权限管理
- 登录认证

## 六、风险与对策

| 风险 | 可能性 | 对策 |
|------|--------|------|
| 后端未及时加字段 | 中 | 前端默认按 Markdown 处理，不影响现有功能 |
| JSON 体积较大 | 低 | 经实测均在 HTTP 可接受范围 |
| 旧版前端无法读新文档 | 中 | 仅被编辑过的文档会变为新格式，且后端可以提供批量回滚接口 |
| 用户编辑与迁移冲突 | 低 | 数据库层面乐观锁，先编辑的先生效 |

本次迁移完成为以下工作奠定了格式基础：

| 后续功能 | 格式依赖 | 说明 |
|----------|----------|------|

## 八、总结

可行性已验证，方案已明确，风险可控。核心工作量为 9 个文件修改 + 5 个新文件，后端需配合增加 1 个数据库字段和 1 个响应字段。迁移对用户完全透明，不中断服务。
