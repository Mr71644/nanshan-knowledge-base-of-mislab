# 文件树拖拽 — 后端对接分析

> 版本：1.0 | 日期：2026-05-26
> 涉及接口：`PUT /home/sort`、`PUT /home/move` 及相关变更接口

---

## 一、功能概述

文件树拖拽功能需要后端支持两类操作：

| 操作 | 接口 | 场景 |
|------|------|------|
| **同层排序** | `PUT /home/sort` | 在同一父文件夹内，拖拽调整节点的前后顺序 |
| **跨层移动** | `PUT /home/move` | 将文件/文件夹从一个文件夹拖到另一个文件夹中 |

此外，现有的树查询接口和文件创建接口也需要适配排序字段，保证拖拽后的顺序能被持久化和正确返回。

---

## 二、同层排序（PUT /home/sort）

### 2.1 实现逻辑

前端在用户完成同级拖拽后，将该层级下**所有兄弟节点按新顺序排列**发送给后端。后端遍历列表，批量更新每个节点的 `sort_order` 字段为其在数组中的索引值。

**请求参数**：

| 参数 | 说明 |
|------|------|
| `parentFolderId` | 父文件夹 ID，`null` 表示根目录 |
| `orderedIds` | 按新顺序排列的所有兄弟节点，每项含 `id` 和 `status`（类型标识） |

**关键设计决策**：前端每次都发送**完整的有序列表**，而非只发送变更项。这种全量替换策略简化了后端逻辑，避免增量更新时的顺序冲突。

### 2.2 后端需完成的步骤

1. 校验用户对该父级文件夹有编辑权限
2. 根据 `status` 字段定位对应的数据表（文档表、文件夹表、Excel 表、文件表）
3. 在事务中批量更新所有节点的 `sort_order`
4. 返回成功响应

### 2.3 隐含问题

- **完整性未校验**：后端无法确认前端传来的 `orderedIds` 是否包含了该层级下的全部子项。如果前端因 bug 遗漏了某个节点，该节点的 `sort_order` 将保持原值，可能导致排序异常。建议后端增加完整性校验。
- **跨表排序的一致性**：四种类型的节点存储在不同表中，但它们共享同一个排序空间。后端需要在逻辑上保证不同表的 `sort_order` 值互不冲突（例如文件夹 sort_order=1 和文档 sort_order=1 是否会冲突，取决于查询实现）。
- **并发安全**：两个用户同时对同一文件夹下的节点排序，后到的请求会覆盖先到的结果。事务只能保证单次操作的原子性，无法解决这种业务层面的冲突。

## 三、跨层移动（PUT /home/move）

### 3.1 实现逻辑

用户将一个节点从当前位置拖入另一个文件夹时，前端调用此接口。后端根据节点类型定位数据表，更新其 `folder_id` 为目标文件夹 ID，同时将 `sort_order` 设为目标文件夹下的最大值 +1（排在末尾）。

**请求参数**：

| 参数 | 说明 |
|------|------|
| `itemId` | 被移动的文件/文件夹 ID |
| `itemStatus` | 类型：1=文档、2=文件夹、3=Excel、4=文件 |
| `targetFolderId` | 目标文件夹 ID，`null` 表示移到根目录 |

### 3.2 后端需完成的步骤

1. 校验用户对**源文件夹**和**目标文件夹**都有编辑权限
2. 校验目标文件夹存在（除非 `targetFolderId` 为 `null`）
3. **循环引用检测**（仅当移动的是文件夹时）：确保目标文件夹不是被移动文件夹自身或其子文件夹
4. 更新节点的 `folder_id` 和 `sort_order`
5. 返回成功响应

### 3.3 循环引用检测

这是移动操作独有的安全问题。如果允许将文件夹 A 移入文件夹 A 的子文件夹 B 中，会形成循环引用，导致树结构崩溃。

检测方法：从 `targetFolderId` 开始向上遍历父级链，如果遇到 `itemId` 则拒绝操作。具体实现依赖数据库是否支持递归查询（MySQL 8.0+ 的 CTE 或 PostgreSQL）。

### 3.4 隐含问题

- **源权限未传递**：请求体中没有源文件夹 ID。后端需要先根据 `itemId` + `itemStatus` 查询出当前 `folder_id`，再校验用户对源文件夹的权限。这个额外查询增加了接口复杂度。
- **移动后原位置留空**：节点被移走后，原文件夹下的其余节点 `sort_order` 不会自动重排，可能留下不连续的排序值。虽然不影响功能，但长期积累后排序值会越来越稀疏。
- **子树移动的隐含逻辑**：移动文件夹时，其子项的 `folder_id` 无需更新（子项通过文件夹的层级关系间接关联，不是直接关联到顶层）。这个设计简化了移动操作，但也意味着如果未来需要查询某节点所属的最顶层文件夹，需要递归向上查找。
- **前端乐观更新与后端状态不一致的窗口**：前端先更新本地 UI 再调用 API。在 API 响应之前，如果用户快速执行第二次拖拽，操作的将是一份已过期（乐观更新后）的本地树数据。

## 四、数据库变更

### 4.1 新增字段

文档表、文件夹表、Excel 表、文件表四张表均需添加 `sort_order` 字段（INT，默认值 0）。

### 4.2 排序规则

所有返回文件列表的查询统一使用：

```
ORDER BY pinned DESC, sort_order ASC, update_time DESC
```

- 置顶项始终在最前
- 其次按用户自定义排序
- `sort_order` 相同时按更新时间降序兜底（兼容旧数据）

### 4.3 新建内容的排序

所有创建新文件/文件夹的接口，需将 `sort_order` 设为同级最大值 +1，确保新内容出现在末尾。

涉及接口：`POST /folder/add`、`POST /text/add`、`POST /excel/upload`、`POST /minio/upload`、`POST /minio/upload/batch`。

### 4.4 隐含问题

- **旧数据兼容**：所有旧数据的 `sort_order` 为 0，在排序查询中等价。未执行数据迁移前，旧数据会全部按 `update_time` 降序排列，不影响正常使用。但如果用户对包含旧数据的层级执行排序，只有被包含在 `orderedIds` 中的节点会获得新排序值，未包含的节点仍为 0。
- **多表排序值空间**：四种节点存储在不同表中，它们的 `sort_order` 是独立编号还是共享同一编号空间，需要在查询实现中明确。如果查询时需要跨表 UNION 后排序，`sort_order` 应保证全局唯一；如果是分别查询后在应用层合并，则各表独立编号即可。

## 六、安全校验要点

| 校验项 | 涉及接口 | 说明 |
|--------|---------|------|
| 登录态 | 全部 | Bearer Token 校验，401 响应 |
| 编辑权限 | sort、move | sort 校验目标父级文件夹；move 需同时校验源和目标 |
| 目标存在性 | move | `targetFolderId` 对应的文件夹必须存在 |
| 循环引用 | move | 仅文件夹移动时检测，防止移入自身子树 |
| 事务保护 | sort、move | 保证批量更新的原子性 |

## 七、风险与隐患总结

### 高优先级

1. **前端无权限校验 → 后端成为唯一防线**

   拖拽的 `draggable` 属性无条件为 `true`，VIEW 权限用户也可以触发拖拽操作。后端 API 是唯一阻止非授权操作的环节。如果后端权限校验存在遗漏，数据将直接被非法修改。建议后端确保 `PUT /home/sort` 和 `PUT /home/move` 都严格校验编辑权限。

2. **后端缺少 403 响应的约定**

   前端 Axios 拦截器目前只处理 401（未登录），不区分 403（权限不足）。如果后端返回 403，前端会将其作为普通错误处理，提示「移动失败，请重试」。建议前后端统一 403 的处理方式，向用户明确展示「权限不足」的提示。

3. **orderedIds 完整性无校验**

   排序接口未校验传入的节点列表是否包含了该层级下的全部子项。遗漏的节点排序值不会被更新，可能导致显示异常。

### 中优先级

4. **并发排序冲突**

   两个用户同时对同一文件夹排序，后到的请求直接覆盖。缺少乐观锁或版本号机制。

5. **前端乐观更新与快速连续操作**

   前端先更新本地树再调 API。在 API 未返回时执行第二次拖拽，操作基于已过期但乐观更新后的本地数据，可能导致请求参数与实际服务端状态不一致。

6. **搜索状态下的拖拽**

   搜索时文件树被过滤显示，但底层树数据不变。用户在搜索结果中拖拽，拖拽目标和实际层级关系可能不符预期。

### 低优先级

7. **排序值长期不重整**

   移动操作后原位置的排序值不连续，长期使用后排序值会越来越稀疏。不影响功能，但如果未来需要基于排序值做范围查询可能造成困扰。

8. **循环引用检测的数据库依赖**

   递归查询父级链需要数据库支持（MySQL 8.0+ CTE）。如果使用较旧的数据库版本，需要在应用层实现递归查找，增加代码复杂度。

---

## 八、改进建议

| 优先级 | 建议 |
|--------|------|
| 高 | 后端排序接口增加 `orderedIds` 完整性校验 |
| 高 | 前端 Axios 拦截器增加 403 响应处理，区分「未登录」和「权限不足」 |
| 高 | 前端拖拽增加 `permissionType` 校验，VIEW 用户禁用拖拽 |
| 中 | 前端在搜索状态下禁用拖拽功能 |
| 中 | API 请求期间禁用二次拖拽（防快速连续操作） |
| 低 | 定期执行排序值重整脚本（将稀疏值压缩为连续整数） |
