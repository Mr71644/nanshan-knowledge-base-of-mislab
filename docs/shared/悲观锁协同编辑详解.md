## 一、根本思想：互斥代替合并

三大协同流派（OT / CRDT / 悲观锁）的本质差异只有一句话：

| 流派 | 冲突哲学 | 一致性来源 |
|---|---|---|
| OT | 冲突发生后**变换**双方操作使结果收敛 | 服务器全序 + transform 算法 |
| CRDT | 冲突发生后按**数学规则**确定性合并 | 数据结构内置合并语义 |
| 悲观锁 | **根本不允许并发写发生** | 互斥（同一时刻一个区域只有一个写者） |

OT 和 CRDT 都属于**乐观并发控制**——先编辑，后解决冲突；悲观锁是**悲观并发控制**——编辑前先确认独占权，拿不到就不许写。它不解决冲突，因为它让冲突在物理上不可能发生（至少在守规矩的客户端之间）。

> 术语澄清：本文的"悲观锁"指**应用层的咨询锁（advisory lock）**，不是数据库的 `SELECT ... FOR UPDATE`。数据库锁/Redis 锁只是它可能的实现基底，锁的是"用户对某片表格区域的编辑权"这个业务概念。

## 二、锁粒度光谱——第一个核心决策

粒度是悲观锁方案里影响最大的设计变量，从粗到细是一条光谱：

| 粒度 | 并发写者数 | 锁数量级 | 前端复杂度 | 典型形态 |
|---|---|---|---|---|
| **文件级** | 1 | 每文档 1 把 | 极低（整页只读切换） | SharePoint 经典 check-out/check-in、旧版 wiki"他人正在编辑"横幅 |
| **工作表级** | 每 sheet 1 个 | 少 | 低 | 小型自研项目常见 |
| **区域级（range）** | 数个 | 中 | 中（区域相交判定 + 只读态渲染） | 腾讯文档早期、表单类产品 |
| **单元格级** | 理论上 = 用户数 | 大 | 高（锁表维护、头像气泡逐格显示） | 运行时编辑锁的常见粒度 |

几个关键权衡：

- **粒度越细，互斥越精准，但锁管理成本指数上升**：心跳、广播、UI 渲染都随锁数量线性增长。10 人同时编辑、每人锁 1 个单元格没问题；填充柄一次拖 500 格、粘贴一整块，就是 500 把锁——所以实践中单元格锁总是配合**区域锁**做合并。
- **文件级锁便宜到不需要 WebSocket**：打开文档时一个 HTTP POST 申请、关闭时释放，剩下的就是"占用中→整页只读"。它能直接叠在"全量加载 + 整份保存"的传统架构上，一行存储模型都不用改——这是它能当 MVP 的原因。
- **粒度选择的经验法则**：编辑密度低（几个人偶尔改同一张表）选文件级/表级；编辑密度高就该怀疑悲观锁本身是不是对的选型了。

## 三、锁的生命周期与协议

一把锁从申请到释放的完整状态机：

```
             acquire(reqId)              grant
  ┌──────┐ ───────────────▶ ┌──────────┐ ────▶ ┌─────────┐
  │ IDLE │                  │ACQUIRING │        │ HOLDING │◀─┐
  └──────┘ ◀─────────────── └──────────┘ ◀────  └─────────┘  │ renew/心跳
    ▲  ▲      deny(带占用者)     ▲                      │      │
    │  └────────────────────────┘                LOCK_LOST │
    │             release(正常提交/离开)                   │(TTL 过期被他人抢走)
    └──────────────────────────────────────────────────────┘
```

协议消息：

```
C→S:   {type:"lock.acquire", docId, sheetId, range:{r1,c1,r2,c2}, reqId}
S→C:   {type:"lock.granted", reqId, lockId, token, ttl:10}
     | {type:"lock.denied",  reqId, owner:{userId,name,avatar}, conflictRange}
广播:  {type:"lock.changed", range, owner, ttl}      ← 新锁产生
       {type:"lock.released", range, lockId}         ← 锁释放/过期

C→S:   {type:"lock.renew", lockId, token}            ← 每 ~3s
S→C:   {type:"lock.renewed", lockId, ttl} | {type:"lock.revoked", lockId}

C→S:   {type:"lock.release", lockId, token}          ← 正常释放
beacon: navigator.sendBeacon("/lock/release", ...)   ← beforeunload 兜底
```

逐字段讲设计意图：

- **`reqId`（幂等键）**：网络超时后客户端重试 acquire，服务器按 reqId 去重，否则一次重试可能拿到两把锁。
- **`token`（持有者凭证）**：每次授权生成唯一 token。**续租和释放必须带 token 且服务器校验**——防止 A 的锁过期后 B 拿到，A 迟到的心跳把 B 的锁"续"回去（误续）。这也是 fencing token 的雏形（见第六节）。
- **`range` 相交判定**：新申请与任何已锁区域**相交即冲突**，服务器在授予前做区间求交。区域锁还需要**合并**策略：相邻被锁单元格合并成一个大区间，避免锁表碎片化。
- **acquire 竞态**：两人同时申请同一格，服务器侧必须原子裁决（Redis `SET NX` 或 actor 内串行处理），先到先得；后到者收到的 `denied` 里带占用者信息，前端直接渲染"XX 正在编辑"。
- **TTL ≈ 2–3 个心跳周期**：心跳 3s → TTL 10s。这个比例的含义是：允许客户端连续丢 2 次心跳仍保住锁，同时保证崩溃客户端的锁在 ~10s 内自动释放。**TTL 是崩溃恢复机制的全部**——不需要显式的"下线检测"。

## 四、前端实现要点

1. **拦截编辑入口**：双击/回车/F2/粘贴/拖拽填充柄之前查本地锁视图，锁定的格子直接不进编辑态。Univer 这类内核有命令拦截点（beforeCommandExecution）可以做硬拦截。
2. **本地锁视图由广播驱动**：客户端维护一份 `lockMap`（range → owner），所有 `lock.changed/released` 广播实时更新。acquire 前先查本地视图可以省一次 RTT（明显被占就直接不申请），但**裁决权永远在服务器**——本地视图只是优化。
3. **只读态 UI**：被锁格子上色 + 占用者头像气泡（"XX 正在编辑"）。这依赖 presence 数据（谁在线、谁在哪），所以悲观锁方案实际总是和 presence 系统共生——这也是"悲观锁 + presence"说法的来源。
4. **批量操作要么全拿要么不拿**：粘贴 3×5 区域 = 申请这 15 格的 range 锁，部分授予（拿到 12 格）会让"一半能编辑一半不能"的 UI 变得极难做。标准做法是原子授予/原子拒绝。
5. **断连时的 UX 决策**：WebSocket 断了，心跳停了，锁会在 ~10s 后被服务器过期释放。前端应当：立即在 UI 上提示"连接断开，编辑状态可能丢失"，停止接受新编辑；重连后**先拉锁表快照核对**自己还持有哪些锁，再恢复编辑态。
6. **锁被抢的边界**（最棘手的一条）：A 的锁因网络抖动过期 → B 申请成功 → A 的连接恢复。A 此时输入到一半的内容怎么办？常见策略：a) 提示 A 冲突、转入只读，缓冲其未提交输入；b) 软锁哲学下允许提交但提示可能被覆盖（见第六节）。没有完美答案，只有产品取舍。

## 五、后端实现要点

**单锁的 Redis 实现**：

```
# 授予（原子，不存在才设置）
SET lock:{docId}:{sheetId}:{lockId} "{token,range,userId}" NX EX 10

# 续租（必须 Lua 原子：比对 token 再续期，防误续）
if redis.call("GET", key) == token then
  return redis.call("EXPIRE", key, 10)
else return 0 end

# 释放：同样 Lua 比对 token 后 DEL
```

**区域相交判定**：单文档的已锁区域集合放在一个地方串行判定——要么是内存中的 actor（按 docId 粘性路由，与 OT 的单写者模式同构），要么全部经 Redis 原子操作。区域少（通常 < 100）时直接线性遍历求交就够，不需要 interval tree。

**与 OT 后端的关键区别**：锁只要求**互斥**，不要求**全序**。OT 必须把同一文档的所有 op 路由到同一个 actor 做 transform 和 seq 分配；锁裁决只要求"同一把锁同一时刻只有一个 SET NX 成功"，Redis 天然全局原子，**任何节点都能裁决**——所以悲观锁后端可以是无状态的 HTTP 服务 + Redis，不需要粘性路由和文档 actor。这是它"服务端复杂度低"的真正来源。

**广播**：锁变更走 Redis Pub/Sub。注意锁消息是 **ephemeral 且可丢**的——丢一条 `lock.changed` 不需要重放，因为新加入者/重连者总会拉一次**锁表全量快照**。这比 OT 的 op 广播（不可丢、需补拉）宽松得多。

**不持久化**：锁是运行时状态，Redis 重启 = 所有锁释放，用户重新申请即可，完全可接受。这是它相对 OT（op log 必须持久化）的又一简化。

## 六、失败模式——悲观锁真正的难点

| 失败场景 | 后果 | 对策 |
|---|---|---|
| **持锁者崩溃** | 锁悬挂 | TTL 自动过期（核心机制） |
| **僵尸持有者**（GC 停顿/网络分区/笔记本合盖休眠） | 客户端**以为**自己持锁，恢复后提交 → 锁早已易主，写入变成对 B 编辑的无感知覆盖 | 理论对策是 fencing token（单调递增，存储层拒绝旧 token 写入）；Web 场景难做完整，行业折中见下 |
| **心跳风暴** | N 用户 × 多把锁 × 3s 心跳打爆服务器 | 心跳**按用户合并**（一条心跳续该用户全部锁）+ 区域锁合并 |
| **同用户多标签页** | 关一个标签页把另一个标签页的锁也释放了 | 锁按 tab 发 token，或对同用户做引用计数 |
| **锁饥饿** | 某人长期占格不放，他人持续 denied | 等待队列/超时强抢——多数产品**不做**（YAGNI），显示占用者让用户线下沟通 |
| **恶意/buggy 客户端** | 直接调保存接口绕过锁 | 锁根本拦不住——它只是约定 |

其中"僵尸持有者"是整个悲观锁方案的理论软肋，值得展开：**在异步网络里，"硬"悲观锁是不可能的**——消息延迟可以任意大，服务器永远无法区分"持有者崩溃了"和"持有者的心跳还在路上"，TTL 过期释放是唯一选择，而过期释放就意味着可能误杀一个活着的持有者。这就是分布式系统里 Chubby/租约/fencing token 那一整套经典问题的来源。

**行业的实际答案：软锁（advisory lock）**。承认锁只做两件事——**前端拦截 + 占用提示**——不给硬保证；最终落盘用版本号检查（保存时带 `baseVersion`，不匹配则拒绝）或 LWW 兜底。这样僵尸持有者最坏情况退化为"和 LWW 一样的覆盖"，而正常路径上 99% 的冲突已经被锁挡掉了。工程上这是一个非常干净的分层：**互斥是尽力而为的 UX 层，一致性是存储层的版本检查**。

## 七、行业案例定位

- **SharePoint check-out/check-in**：文件级悲观锁的教科书形态——签出后他人完全只读，签入才释放。证明文件级锁在低协作密度下可用几十年。
- **Excel Online「保护范围」/ 飞书「设置保护范围」**：这些**不是**协同锁，而是**权限型静态锁**（配置谁永远不能改哪片区域）。产品把"锁"这个词用于权限配置，实时并发层另由 OT/merge 处理——这是理解行业格局的关键区分。
- **OnlyOffice Strict 模式**：悲观思想在文档编辑器里的变体——锁的粒度是**段落**，锁定段落他人只读，保存后释放。它和 Fast 模式（实时合并）并存，把选择权交给用户，是"锁 vs 合并"两条路线在同一产品里的直接对照。
- **腾讯文档早期 → OT**：典型的演进路径——锁起家，用户量上来后并发编辑需求超过锁的承受力，转向 OT。锁与 presence 层保留。
- **表单/数据库类产品**（多见于内部系统、低代码平台）：字段级的"XX 正在编辑"提示 = 标准软锁 + presence。

## 八、何时选它——决策判据

**选悲观锁，当且仅当大部分条件成立：**

- 快速 MVP，人力/时间预算小（后端无状态 + Redis，前端只读态切换）
- 协作密度低：几个人、偶尔同时打开、冲突本来就罕见
- 不需要离线编辑（悲观锁与离线天然互斥——没有服务器就没有锁）
- 团队能接受"被人占用就等着"的交互模型
- 保存层愿意加一个版本号检查做兜底（强烈建议，把软锁的最后一块补上）

**不选它，当：** 高并发同表编辑是核心场景、需要"无感"的实时协同体验（锁的申请 RTT 会打断键入流）、或产品要求离线/local-first——这三条分别指向 OT、OT、CRDT。

**演进路径**：悲观锁 MVP → 保存层版本号 → 保留锁与 presence 作为 UX 层 → 协同算法层另行升级 OT。锁和 presence 在任何后端方案下都不浪费，这是它作为起点的额外价值。

**一句话总结**：悲观锁用**互斥的确定性**换掉了 OT 的 transform 矩阵和 CRDT 的元数据膨胀，代价是并发度和那一个永远修不干净的僵尸持有者问题，而行业用"软锁 + 存储层版本检查"的分层把这个代价压到了可接受。
