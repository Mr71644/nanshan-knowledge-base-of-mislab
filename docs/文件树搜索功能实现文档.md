# 文件树搜索功能 — 实现文档

## 1. 功能概述

在 Home 侧边栏的文件树上方添加搜索输入框，用户输入关键词后：

- **实时过滤**：基于已加载的树数据，按名称进行大小写不敏感匹配
- **高亮显示**：匹配的文本片段用黄色背景高亮标记
- **自动展开**：匹配节点的所有父级路径自动展开
- **淡化非匹配项**：未匹配且非祖先的节点降低透明度（0.35），保持结构可见
- **一键清除**：点击输入框的 × 按钮恢复完整树

纯前端实现，无需后端 API 改动，不新增文件。

## 3. 核心架构

### 3.1 数据流

```
用户输入 → searchText 更新 → useMemo 重新计算 → walkFilter 递归遍历
                                                          ↓
                                              { filteredMatchKeys, searchExpandedKeys }
                                                    ↓              ↓
                                          renderTitle(高亮/淡化)   expandedKeys(自动展开)
```

### 3.2 walkFilter 递归过滤函数

搜索的"大脑"，遍历整棵树找出匹配节点：

```
walkFilter(items, keyword, parentKeys) → { matchKeys: Set, ancestorKeys: Set }
```

**算法逻辑**：
- 对每个节点，用 `item.name.toLowerCase().includes(keyword)` 判断是否匹配
- 递归处理 `item.children`
- 节点"相关"条件：自身名称匹配 **或** 子孙中有匹配项
- `parentKeys` 沿递归路径累积文件夹 key（仅 status=2 的节点是文件夹），当深层节点匹配时，所有上级文件夹 key 已收集

**返回值**：
- `matchKeys` — 直接匹配的节点 key 集合（用于高亮）
- `ancestorKeys` — 匹配节点的所有祖先 key 集合（用于自动展开）

### 3.3 useMemo 派生数据

连接用户输入和过滤结果的"触发器"：

```jsx
const { filteredMatchKeys, searchExpandedKeys } = useMemo(() => {
    const trimmed = searchText.trim().toLowerCase()
    if (!trimmed) return { filteredMatchKeys: new Set(), searchExpandedKeys: null }
    const { matchKeys, ancestorKeys } = walkFilter(folderTree, trimmed, [])
    return { filteredMatchKeys: matchKeys, searchExpandedKeys: ancestorKeys }
}, [searchText, folderTree])
```

- 搜索文本为空 → 空 Set + null（搜索未激活）
- 搜索文本非空 → 调用 `walkFilter`，将返回值映射为组件内使用的变量名
- 仅在 `searchText` 或 `folderTree` 变化时重新计算

### 3.4 消费结果

**expandedKeys** — 搜索激活时合并祖先 key，实现自动展开路径：
```jsx
expandedKeys={searchExpandedKeys ? [...new Set([...openKeys, ...searchExpandedKeys])] : openKeys}
```

**renderTitle** — 根据节点状态决定渲染方式：

| 条件 | 效果 |
|---|---|
| `filteredMatchKeys.has(key)` | 用 `indexOf` 循环拆分名称，匹配片段用黄色背景 span 包裹 |
| 不匹配且非祖先 | 添加 `opacity: 0.35` 淡化 |
| 搜索未激活 | 原样显示 |

### 4.2 添加过滤辅助函数（第 68 行之后）

在 `findParentKeysByTargetKey` 函数之后、`const Home = () => {` 之前，插入：

```jsx
const walkFilter = (items, keyword, parentKeys = []) => {
    let matchKeys = new Set()
    let ancestorKeys = new Set()

    for (const item of items) {
        const key = getMenuKeyByItem(item)
        const currentParentKeys = item.status === 2 ? [...parentKeys, key] : parentKeys
        const nameMatch = item.name.toLowerCase().includes(keyword)

        if (item.children && item.children.length > 0) {
            const childResult = walkFilter(item.children, keyword, currentParentKeys)
            if (nameMatch || childResult.matchKeys.size > 0) {
                if (nameMatch) matchKeys.add(key)
                matchKeys = new Set([...matchKeys, ...childResult.matchKeys])
                ancestorKeys = new Set([...ancestorKeys, ...currentParentKeys, ...childResult.ancestorKeys])
            }
        } else {
            if (nameMatch) {
                matchKeys.add(key)
                ancestorKeys = new Set([...ancestorKeys, ...currentParentKeys])
            }
        }
    }

    return { matchKeys, ancestorKeys }
}
```

**说明**：
- 复用已有的 `getMenuKeyByItem()` 计算节点 key，与现有树结构一致
- `matchKeys`：直接匹配的节点 key 集合（用于高亮）
- `ancestorKeys`：匹配节点的所有祖先 key 集合（用于自动展开）
- `parentKeys` 参数追踪从根到当前的文件夹 key 路径（仅 status=2 的节点是文件夹，会被展开）

### 4.5 替换 renderTitle（第 235-242 行）

```jsx
// 改动后
const renderTitle = (nodeData) => {
    const item = nodeData.rawData
    const key = nodeData.key
    const trimmed = searchText.trim()
    const isSearching = trimmed.length > 0
    const isMatch = filteredMatchKeys.has(key)
    const isAncestorOrSelf = searchExpandedKeys && searchExpandedKeys.has(key)

    let titleContent
    if (isSearching && isMatch) {
        const lowerName = item.name.toLowerCase()
        const lowerKeyword = trimmed.toLowerCase()
        const parts = []
        let lastIndex = 0
        let idx = lowerName.indexOf(lowerKeyword)
        while (idx !== -1) {
            if (idx > lastIndex) parts.push(item.name.slice(lastIndex, idx))
            parts.push(
                <span key={idx} className={style.searchHighlight}>
                    {item.name.slice(idx, idx + trimmed.length)}
                </span>
            )
            lastIndex = idx + trimmed.length
            idx = lowerName.indexOf(lowerKeyword, lastIndex)
        }
        if (lastIndex < item.name.length) parts.push(item.name.slice(lastIndex))
        titleContent = parts
    } else {
        titleContent = item.name
    }

    const dimmed = isSearching && !isMatch && !isAncestorOrSelf

    return (
        <Tooltip title={item.name}>
            <span className={dimmed ? style.treeNodeDimmed : undefined}>
                {titleContent}
            </span>
        </Tooltip>
    )
}
```

## 5. 技术选型：前端过滤 vs 后端搜索

### 性能特征

| 指标 | 前端过滤（当前方案） |
|---|---|
| 时间复杂度 | O(n)，n = 树节点总数，每次输入遍历一次 |
| 空间复杂度 | O(m)，m = 匹配节点 + 祖先数量（两个 Set） |
| 触发频率 | 每次按键 → useMemo 重算 |
| 实际耗时 | 几十到几百节点 < 1ms；上千节点约 5-10ms |

### 前端 vs 后端对比

| 维度 | 前端过滤（当前方案） | 后端 API 搜索 |
|---|---|---|
| 响应速度 | 即时（< 1ms） | 网络往返 50-200ms + 服务器计算 |
| 用户体验 | 无延迟，逐字响应 | 需 debounce/防抖，输入后等待 |
| 搜索范围 | 仅已加载的树节点名称 | 可搜内容、全文检索、模糊匹配 |
| 服务器压力 | 无 | 每次搜索都产生请求 |
| 数据实时性 | 取决于上次 `getFolderTree` 的时间 | 每次搜索查数据库，始终最新 |
| 离线/弱网 | 完全可用 | 不可用 |
| 大规模数据 | 节点超过几千可能卡顿 | 数据库索引，百万级也没问题 |

### 选型理由

**1. 数据规模适配** — 知识库文件树典型规模在几十到几百个节点，前端遍历在亚毫秒级完成，后端搜索的优势（数据库索引、分页、全文检索）在此规模下无法体现。

**2. 交互体验优先** — 搜索的核心体验是"边输入边看到结果"。前端过滤是同步的，每次按键即时响应；后端搜索即使加了 debounce 也会有 100-300ms 的感知延迟。

**3. 实现成本最低** — 不需要新增 API、不需要改后端、不需要处理异步状态（loading/error），代码改动集中在 3 个文件约 50 行。

### 何时应考虑切换后端搜索

- 节点规模超过 5000+，前端遍历出现卡顿
- 需要搜索文件**内容**（如文档正文、Excel 内容）
- 需要模糊匹配、拼音搜索、分词搜索
- 多用户协作场景下树结构变化频繁，前端缓存经常过期

## 6. 交互行为说明

### 清除/重置

- 点击 × 按钮 或 删除所有文字 → `searchText` 为空
- `useMemo` 返回 `searchExpandedKeys: null`
- Tree 恢复使用 `openKeys`（保留用户之前手动展开的状态）
- 所有节点恢复正常显示

### 边界情况

| 场景 | 处理方式 |
|---|---|
| 树为空 | `walkFilter` 返回空 Set，无影响 |
| 侧边栏折叠 | 搜索框隐藏，无法输入 |
| 搜索中拖拽节点 | `folderTree` 变化自动触发 `useMemo` 重算 |
| 特殊字符（`.`、`*` 等） | 使用 `includes/indexOf` 匹配，非正则，无需转义 |
| 用户手动展开/折叠 | 搜索中展开操作与自动展开合并；清除搜索后保留用户操作 |

## 7. 已修复问题

### walkFilter 返回值解构错误

**现象**：页面报错 `Cannot read properties of undefined (reading 'has')`

**原因**：`walkFilter` 返回 `{ matchKeys, ancestorKeys }`，但 `useMemo` 中直接解构为 `{ filteredMatchKeys, searchExpandedKeys }`，属性名不匹配导致值为 undefined。

**修复**：在 `useMemo` 中先解构 `walkFilter` 的返回值，再映射为组件内使用的变量名：

```jsx
// 修复前（错误）
return walkFilter(folderTree, trimmed, [])

// 修复后（正确）
const { matchKeys, ancestorKeys } = walkFilter(folderTree, trimmed, [])
return { filteredMatchKeys: matchKeys, searchExpandedKeys: ancestorKeys }
```
